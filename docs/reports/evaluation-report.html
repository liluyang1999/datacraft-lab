一、执行摘要

总体结论：L8 已修复 Windows 原生无障碍生命周期异常，并在 Windows、Linux 最终各 20 次原生缓存启动中全部达到 1.5 s 预算。两平台完整桌面门禁通过，远端 CI 的本轮结果见 4.5；测量条件和密集 UIA 读取的性能边界见 4.4、第八章。CLI、HTTP API 与 Airflow 共用同一个 DataJob 契约和执行引擎，失败语义统一；8 个 Maven 模块按职责分为 core、io、processing、interfaces 四组，越界依赖在构建的 validate 阶段即失败；质量门禁不允许任何编译、类型检查或 Shell 检查警告，CI/CD 逻辑集中在 cicd/，可以脱离 GitHub Actions 在本机复现；流水线步骤的失败原因写入公开注解；Compose 栈与 Swarm 栈在 L7 本机及远端 CI 中均实际部署过；所有镜像运行按版本与校验和固定的 Temurin 25.0.5。桌面控制台“数艺工坊”在一个窗口里查看与操作两个后台，它只是客户端，默认后端构建不包含桌面工程。

主要优势
  • 一个契约、一个引擎、三种入口，新作业注册一次即可在 CLI、API 与 Airflow 中使用（第三章）。
  • 模块边界、JDK 版本下限与零警告由构建强制，而不是靠约定（3.2、4.3）。
  • 317 项后端 JVM 测试、118 项桌面测试（含 11 项端到端）与 257 项脚本、文档、DAG 测试。平台测试和端到端测试分组执行；默认门禁下限为 Linux 后端 310、Windows 后端 300，桌面 Linux 104、Windows 106 项（4.2、4.4）。
  • 桌面控制台“数艺工坊”（JavaFX 25）：本机数据只在 ~/.datacraft 的 SQLite 里，令牌与口令加密保存；界面测试覆盖每个视图的两种主题与 FX 线程的停顿，端到端测试对真实的引擎 API 与 Compose 部署通过（3.7）。
主要风险
  • HTTP API 现在要求令牌，但它是明文 HTTP 上的共享密钥，仍然只应绑定回环地址或放在终结 TLS 的网关之后（第五章）。
  • Swarm 栈在 CI 前置门禁通过后部署并升级；两个节点的情形在此前的本机记录中手工验证过一次（放置、路由网格、节点之间的 ESP 加密），不在 CI 之中。默认拓扑仍把所有服务固定在一台数据节点上，不是高可用方案；节点故障、真实主机之间的防火墙与共享存储没有验证（3.5、第八章）。
  • 所有 Airflow 容器共享全部机密，DAG、CLI 与 Spark 属于管理员级可信代码；Spark 4.2.0 自带的依赖有尚未修复的公告，要等 4.2.1（第五章、第八章）。

云平台结论（第六章）：每月运行不足 227.5 小时时选 Oracle OCI A1 按需（60 小时约 $4.79/月）；常开或超过 227.5 小时选腾讯云 Lighthouse 入门型（$10.15/月）；必须使用 AWS 时选 Lightsail 8 GB（$44.15/月）。托管 Airflow 与 Cloudflare 运行时不采用，R2 只用于备份。所有价格为 2026-09-19 的公开价快照，尚未购买任何云资源。

上一轮（2026-10-27）的历史记录：其一是上一轮唯一等待上游的版本问题：官方 Temurin 与 Maven 镜像在 Temurin 25.0.5 发布五天后仍是 25.0.4.1，本轮不再等它们，新的 Dockerfile.temurin 按版本与 SHA-256 固定 Temurin 25.0.5+8，构建镜像与三个运行镜像都换上它，构建下限提高到 25.0.5（不兼容），公告工作流每周向 Adoptium 核对是否有更新的版本。其二是新增的桌面控制台“数艺工坊”（desktop/，JavaFX 25.0.5）：查看两个后台是否健康、带参数运行作业、触发与跟踪 Airflow 流水线、查看结果与日志；本机数据只在 ~/.datacraft 的 SQLite 里，不新增后台接口。它先规划与设计、再分轮实现，一路只读代码审阅的 13 处发现全部修复；第一次 CI 运行之后，又补上了桌面套件的测试数下限与桌面依赖的公告检查。逐项对应见附录 A；上一轮（2026-10-26）的明细见附录 B。

3.3 数据处理与数据根约束

  • 两类计算，各守其位：Spark 作业处理大文件，Spark 以 provided 作用域引入并由 spark-submit 提供，CLI 瘦 jar 因此只有约 9 MB；纯 JVM 作业处理小文件，不需要 Spark，可以在只含 JRE 的 API 镜像中运行。csv-profile 读取前检查文件大小（默认上限 64 MiB）与堆内存预算，超出时提示改用 Spark 的 row-count。
  • 数据根约束：设置 DATACRAFT_DATA_ROOT 后，纯 JVM 作业的输入必须严格位于数据根之内，并通过以数据根真实路径为根的 LocalStorageService 读取，拒绝指向根外的符号链接与目录联接；Spark 转换的输入输出同样受约束，并拒绝 glob 字符与输入输出重叠。API 镜像与部署栈中的 Airflow 服务都设置了数据根，API 以只读方式挂载数据卷。
  • 先校验、后启动：Spark 作业在启动会话之前完成参数校验，参数名只差大小写也会被拒绝；CSV 与 JSON 以 FAILFAST 方式读取，质量门槛（例如 expectedRows）不符即失败，不会静默退回默认值。CSV 的编码由 encoding 参数给出（默认 UTF-8，可以是 GBK、Big5、Shift_JIS 等与 ASCII 兼容的字符集）；读取之前先把输入按原始字节逐行严格解码，不符合编码的文件直接失败并指出文件，而不是像 Spark 自身那样替换成 U+FFFD 后报告成功；以 UTF-8 字节序标记开头的文件只按 UTF-8 读取。
  • 边界：这是应用层防护，不是操作系统沙箱，硬链接和并发的恶意改动无法检测，数据根仍需要文件系统权限配合；row-count、spark-version、echo、noop 不受数据根约束。

3.4 部署拓扑

Swarm 模板：多机部署使用 CeleryExecutor 与 Redis，但所有服务都固定在 DATACRAFT_DATA_NODE 这一台数据节点上，因为数据卷是节点本地卷；API 不发布端口，只在覆盖网络内可达，并要求令牌；Redis 要求口令，覆盖网络以加密方式创建。CI 的 containers 作业在单节点 Swarm 上把这套栈按部署教程部署一遍、再升级一遍（见下文的流水线表）。它仍然不是高可用方案：跨节点扩展先要有共享存储，本轮未重测多节点放置、故障切换与跨主机网络，不把此前的手动演练当作高可用证明。

3.5 构建与 CI/CD 流水线

Maven 反应堆由根 POM 统一管理版本与质量门禁，./mvnw verify 依次执行 Enforcer（JDK 25.0.5 以上、Maven 3.9 以上、插件版本固定、禁止 POM 仓库、禁止有漏洞的 Jackson、模块边界）、编译（javac -Xlint:all 与 failOnWarning，scalac -Werror）、Spotless 与 Checkstyle、JUnit 与 ScalaTest，以及瘦 jar 打包。GitHub 只从 .github/workflows 读取工作流，因此 ci.yml 只负责触发条件、运行环境、固定版本的工具链与作业编排，每一步只执行一条命令：cicd/ 下的脚本、tests/ 下的测试入口，或单个工具（Maven Wrapper、pyright）。cicd/ 放流水线执行的内容，tests/ 放测试运行器或开发者运行的套件，deploy/scripts 放运维在主机上执行的脚本。

作业日志需要仓库权限才能读取，而一次运行的注解是公开的。因此工作流把 cicd/step.py 设为所有 run: 步骤的默认 shell：它原样执行步骤并保持退出码，步骤失败时追加一条错误注解，内容是失败的命令、最先指出错误的若干行输出与最后 30 行输出；部署类脚本在拆除失败的栈之前，用 diagnose 把各服务的日志与状态分组输出，每组成为一条独立的注解；通过的检查用 notice 记下证据（各模块实际执行的测试数、运行镜像的 Java 版本、Compose 冒烟与 Swarm 演练的结论）。另一个工作流 advisories.yml 每周一运行 cicd/security/check_advisories.py，向 OSV 查询每一个固定的依赖与 Action 是否有新公告，再由 check_temurin.py 向 Adoptium 核对镜像固定的 Temurin 是否仍是最新版本，不引入会自动提交的机器人。

tests/ci/test_workflow.py 保证每个 run: 只有一条命令（不允许多行块，也不允许 &&、| 等运算符），工作流与 Makefile 引用的脚本都存在，cicd/ 里的每个文件都被使用（注释里的提及不算）且没有被 git 忽略，cicd/ 与 deploy/scripts/ 之外不出现 Shell 脚本；每个作业先检出再执行步骤，没有作业或步骤自设 shell 或 working-directory。

3.7 桌面控制台“数艺工坊”

desktop/ 是一个独立的 Maven 工程（父 POM 是根 POM，默认后端反应堆不含它；-Pdesktop -pl :datacraft-desktop -am 只构建父工程与桌面），用 JavaFX 25.0.5 在 JDK 25 上运行：在一个窗口里看两个后台是否健康、带参数运行作业、触发与跟踪 Airflow 流水线、查看结果与任务日志。它只调用后台现有的接口，即引擎 API 的 /health 与 /jobs、Airflow 3.3.2 的 REST API v2；它不保存业务数据，本机只有 ~/.datacraft 下的设置、连接配置、参数预设与有上限的缓存。

层职责线程
界面 ui侧栏、顶栏与五个视图（总览、作业、流水线、活动、设置），侧滑面板与通知；“蓝晒”冷色调的浅色与深色两套主题FX 线程，只做界面
视图模型 viewmodel可观察的状态与命令；轮询结果按主键就地更新，同类结果只应用最新的一次FX 线程（测试中由测试控制的队列代替）
服务 service连接配置与会话、两个后台的健康检查、作业运行、流水线、活动记录；只轮询屏幕上的数据，失败退避到 30 秒一个到点线程，请求在虚拟线程上

依赖只向下：服务、客户端与存储都不引用 JavaFX。流畅度的预算（视图切换不超过 100 ms、FX 线程单次停顿不超过 50 ms、主题切换不超过 100 ms）由界面测试检查，首帧时间每轮记录；打包脚本用 jlink 与 jpackage 生成自带运行时的应用目录，并用一次启动训练 JDK 25 的 AOT 缓存。细节见附录 A.3 与 docs/desktop。

    八、残余风险与路线图

    优先级事项影响建议
    P2API 令牌经明文 HTTP 传输能读到流量的一方可以取得令牌；令牌是所有调用方共用的一个密钥保持回环绑定，经 SSH 隧道访问；对外暴露前在前面加终结 TLS 的网关
    P2Spark 4.2.0 自带依赖的公告Spark 自带的 Jackson 2.21.2 在 OSV 中有 19 条公告（databind 16 条、core 3 条），CVE-2026-110879 也影响它；Netty、Jetty 也有公告。spark-submit 先加载 Spark 自带的 Jackson，本项目的升级管不到 Spark 作业的进程；当前配置下不可达。2026-10-26 复核时 Spark 仍只有 4.2.0不发布 Spark UI 与 RPC 端口；Spark 4.2.1 发布后升级
    P2机密在 Airflow 容器间共享任一任务代码都能读取全部机密，包括 JVM API 的令牌与 Redis 口令。只对任务隐藏其中几项意义不大：数据库口令与 Fernet 密钥足以改写元数据、解密连接视为可信代码边界；多租户前把 worker 与元数据库的凭据分开，再做机密隔离
    P3多节点 Swarm 只做过一次手工验证两个嵌套引擎在一台机器上：放置、路由网格与节点之间的 ESP 通过。它不在 CI 里，脚本或 Docker 版本变化之后不会自动重验；真实主机之间的防火墙、节点故障之后的行为与共享存储没有验证；默认拓扑仍把所有服务固定在一台数据节点上扩展到多机前在真实主机上按部署教程演练一次，并在节点之间放行 ESP（IP 协议 50）；需要长期保障时把两节点试验做成可以重复运行的脚本
    P3SFTP 客户端的两个限度JVM 的 SftpClient 对保持 SSH 连接却不应答请求的服务器没有超时；上传是原地写入，失败会留下不完整的远端文件。目前没有作业使用这个客户端，Airflow 的 SFTP 下载走的是 provider第一个使用它的作业出现时：在外层为调用设时限，上传到临时名称再重命名
    P3CSV 编码检查的两个限度检查要把输入多读一遍；编码指错但字节恰好合法时无法识别（没有字节序标记的 UTF-8 文本总是合法的 ISO-8859-1）。引号内的 CRLF 仍被存为 LF为数据源固定并写明编码；对结果有疑问时用 csv-profile 或抽样核对
    P3公告检查的覆盖范围每周的检查只看直接固定的 32 个版本（本轮起含桌面工程的 JavaFX 与 sqlite-jdbc），不含 Spark 与 Airflow 的传递依赖，也不含基础镜像；只写在发布说明里的漏洞查不到（10-26 核对的 Jackson CVE 就是这样）。2026-10-26 手工查询了官方 Airflow 镜像的 440 个 Python 包：18 个有公告，其中 16 个本部署触及不到，等下一个 Airflow 版本（附录 B.3）关注 Spark、Airflow 与 Jackson 的发行说明；Airflow 发布新版本后去掉 security-overrides.txt 里约束已经覆盖的行；需要可重复的镜像时再固定 digest 并配套更新流程
    P3Airflow 上游的弃用提示Airflow 3.3.2 读取 .airflowignore 时，其自身代码触发 pathspec 1.1.1 的 DeprecationWarning，不影响行为；2026-10-26 复核时 3.3.2 仍是最新版等待 Airflow 上游修复；改用 regexp 忽略语法的收益不抵配置改动
    P3部署上的三处约定Compose 项目名取自目录名 compose，同一主机上的第二份检出会共用容器与数据卷；修改 .env 后重跑启动脚本会重建全部 Airflow 容器，运行中的任务只有 10 秒；从最早版本（PostgreSQL 16 的卷布局）升级的步骤只用 postgres:18 验证过两个环节，没有做完整演练。三处都已写入部署教程一台主机一份部署；挑没有任务运行的时候改配置；从最早的版本升级前先在副本上演练
    P3Spark 会话锁无超时；durationMillis 含排队时间；Lifecycle 仅为标签API 的并发上限使排队的请求数有界（默认最多 3 个在等）；API 镜像不含 Spark，当前部署拓扑下不触发引入 HTTP 侧 Spark 服务或多租户时再处理

    C.5 部署与升级时要注意的变化

    • Swarm 部署的 .env 必须是纯文本：swarm-deploy.sh 现在拒绝带引号、空格、$、#、分号或反斜杠的值，并指出行号与变量名；把引号去掉即可。deployment_env.py init 生成的文件满足要求。Compose 部署不受影响。
    • override 文件现在会被检查：放在 deploy/compose 里的 docker-compose.override.yml 以前只在启动时生效，现在预检也会读取它；把 API 发布到回环之外或给它可写挂载的 override 会在启动前被拒绝。
    • 数据库口令不能是占位符：以 change-me 或 please-change 开头的口令不再通过预检，不论多长。
    • 一台主机只运行一份 Compose 部署：项目名取自目录名 compose，同一主机上的第二份检出会与第一份共用容器和数据卷；确需第二份时为它导出不同的 COMPOSE_PROJECT_NAME 与端口。
    • 修改 .env 要挑没有任务运行的时候：再次运行 compose-up.sh 会重建全部 Airflow 容器，正在运行的任务只有 10 秒的停止宽限。
    • 从最早的版本升级：数据库卷挂在 /var/lib/postgresql/data 的旧部署要按教程新增的一步，把升级前的备份恢复到新卷。
    • Swarm 栈的 Spark 默认并行度：.env 里没有 DATACRAFT_SPARK_MASTER 一行时，现在是 local[2] 而不是 local[*]。
