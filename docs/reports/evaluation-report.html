一、执行摘要

总体结论：datacraft-lab 已达到“个人单机数据处理平台可以放心使用和部署”的水平。CLI、HTTP API 与 Airflow 共用同一个 DataJob 契约和执行引擎，失败语义统一；8 个 Maven 模块按职责分为 core、io、processing、interfaces 四组，越界依赖在构建的 validate 阶段即失败；质量门禁不允许任何编译、类型检查或 Shell 检查警告，CI/CD 逻辑集中在 cicd/，可以脱离 GitHub Actions 在本机复现；流水线每一步失败的原因都会写成公开注解，不需要仓库权限就能读到；Compose 栈与 Swarm 栈都在 CI 上真实部署。

主要优势
  • 一个契约、一个引擎、三种入口，新作业注册一次即可在 CLI、API 与 Airflow 中使用（第三章）。
  • 模块边界、JDK 版本下限与零警告由构建强制，而不是靠约定（3.2、4.3）。
  • 304 项 JVM 测试与 190 项脚本、文档、DAG 测试，平台差异用标签表达，两个平台都没有跳过的测试；JVM 套件本轮在 Windows 与 Linux 各完整跑过一遍，三条 DAG 也在 Linux 本机用真实的 spark-submit 跑通（4.2、4.4）。
主要风险
  • HTTP API 现在要求令牌，但它是明文 HTTP 上的共享密钥，仍然只应绑定回环地址或放在终结 TLS 的网关之后（第五章）。
  • Swarm 栈现在每次推送都在 CI 的单节点 Swarm 上部署并升级一遍，但多节点下的放置、故障切换与节点间流量没有验证过，默认拓扑也仍是把所有服务固定在一台数据节点上，不是高可用方案（3.5、第八章）。
  • 镜像、Compose 与 Swarm 的检查只在 CI 上运行（本机没有 Docker）。本轮起，每一步失败的原因和通过的证据都写入公开注解，不经仓库权限即可读取；要在推送之前验证这些步骤，仍需在本机准备 Docker（3.5、4.5、第八章）。

云平台结论（第六章）：每月运行不足 227.5 小时时选 Oracle OCI A1 按需（60 小时约 $4.79/月）；常开或超过 227.5 小时选腾讯云 Lighthouse 入门型（$10.15/月）；必须使用 AWS 时选 Lightsail 8 GB（$44.15/月）。托管 Airflow 与 Cloudflare 运行时不采用，R2 只用于备份。所有价格为 2026-09-19 的公开价快照，尚未购买任何云资源。

本轮（2026-10-09）完成：逐项处理上一版列出的未做事项与残余风险。HTTP API 增加令牌认证（回环之外没有令牌即拒绝启动）与并发运行上限；Spark 的 CSV 读取增加 encoding 参数，不符合编码的输入直接失败，不再转出乱码；流水线的每个步骤经过 cicd/step.py，失败原因、失败时的服务状态与通过证据写入公开注解；Swarm 栈第一次被真实部署：CI 在单节点 Swarm 上按部署教程演练部署与升级，栈里的 Redis 加上口令、覆盖网络改为加密；新增每周一次的依赖公告检查；构建升级到 Maven 3.10.0，并消除了它带来的仓库探测警告。推送之前另做了两路独立复核，指出的问题逐条复现并修复。多节点 Swarm 的验证与共享机密的隔离没有变化。逐项对应见附录 A；上一轮（2026-10-07）的 CI 修复与模块复盘见附录 B，2026-09-26 的目录重组见附录 C。

3.3 数据处理与数据根约束

  • 两类计算，各守其位：Spark 作业处理大文件，Spark 以 provided 作用域引入并由 spark-submit 提供，CLI 瘦 jar 因此只有约 9 MB；纯 JVM 作业处理小文件，不需要 Spark，可以在只含 JRE 的 API 镜像中运行。csv-profile 读取前检查文件大小（默认上限 64 MiB）与堆内存预算，超出时提示改用 Spark 的 row-count。
  • 数据根约束：设置 DATACRAFT_DATA_ROOT 后，纯 JVM 作业的输入必须严格位于数据根之内，并通过以数据根真实路径为根的 LocalStorageService 读取，拒绝指向根外的符号链接与目录联接；Spark 转换的输入输出同样受约束，并拒绝 glob 字符与输入输出重叠。API 镜像与部署栈中的 Airflow 服务都设置了数据根，API 以只读方式挂载数据卷。
  • 先校验、后启动：Spark 作业在启动会话之前完成参数校验，参数名只差大小写也会被拒绝；CSV 与 JSON 以 FAILFAST 方式读取，质量门槛（例如 expectedRows）不符即失败，不会静默退回默认值。CSV 的编码由 encoding 参数给出（默认 UTF-8，可以是 GBK、Big5、Shift_JIS 等与 ASCII 兼容的字符集）；读取之前先把输入按原始字节逐行严格解码，不符合编码的文件直接失败并指出文件，而不是像 Spark 自身那样替换成 U+FFFD 后报告成功；以 UTF-8 字节序标记开头的文件只按 UTF-8 读取。
  • 边界：这是应用层防护，不是操作系统沙箱，硬链接和并发的恶意改动无法检测，数据根仍需要文件系统权限配合；row-count、spark-version、echo、noop 不受数据根约束。

3.4 部署拓扑

Swarm 模板：多机部署使用 CeleryExecutor 与 Redis，但所有服务都固定在 DATACRAFT_DATA_NODE 这一台数据节点上，因为数据卷是节点本地卷；API 不发布端口，只在覆盖网络内可达，并要求令牌；Redis 要求口令，覆盖网络以加密方式创建。CI 的 containers 作业在单节点 Swarm 上把这套栈按部署教程部署一遍、再升级一遍（见下文的流水线表）。它仍然不是高可用方案：跨节点扩展先要有共享存储，而多节点下的行为没有验证过。

3.5 构建与 CI/CD 流水线

Maven 反应堆由根 POM 统一管理版本与质量门禁，./mvnw verify 依次执行 Enforcer（JDK 25.0.4.1 以上、Maven 3.9 以上、插件版本固定、禁止 POM 仓库、禁止有漏洞的 Jackson、模块边界）、编译（javac -Xlint:all 与 failOnWarning，scalac -Werror）、Spotless 与 Checkstyle、JUnit 与 ScalaTest，以及瘦 jar 打包。GitHub 只从 .github/workflows 读取工作流，因此 ci.yml 只负责触发条件、运行环境、固定版本的工具链与作业编排，每一步只执行一条命令：cicd/ 下的脚本、tests/ 下的测试入口，或单个工具（Maven Wrapper、pyright）。cicd/ 放流水线执行的内容，tests/ 放测试运行器或开发者运行的套件，deploy/scripts 放运维在主机上执行的脚本。

作业日志需要仓库权限才能读取，而一次运行的注解是公开的。因此工作流把 cicd/step.py 设为所有 run: 步骤的默认 shell：它原样执行步骤并保持退出码，步骤失败时追加一条错误注解，内容是失败的命令、最先指出错误的若干行输出与最后 30 行输出；部署类脚本在拆除失败的栈之前，用 diagnose 把各服务的日志与状态分组输出，每组成为一条独立的注解；通过的检查用 notice 记下证据（各模块实际执行的测试数、运行镜像的 Java 版本、Compose 冒烟与 Swarm 演练的结论）。另一个工作流 advisories.yml 每周一运行 cicd/security/check_advisories.py，向 OSV 查询每一个固定的依赖与 Action 是否有新公告，不引入会自动提交的机器人。

tests/ci/test_workflow.py 保证每个 run: 只有一条命令（不允许多行块，也不允许 &&、| 等运算符），工作流与 Makefile 引用的脚本都存在，cicd/ 里的每个文件都被使用（注释里的提及不算）且没有被 git 忽略，cicd/ 与 deploy/scripts/ 之外不出现 Shell 脚本；每个作业先检出再执行步骤，没有作业或步骤自设 shell 或 working-directory。

    1. 在目标账户与地域确认可售库存和实际报价（腾讯云国际站；OCI 主区域的 A1 容量）。

    验收边界

    部署脚本已经就绪，但没有购买或上线任何云资源。真实云账号权限、库存、网络延迟、用户数据下的性能与 ARM 主机运行都未验证；当前容器运行证据来自 Linux amd64 的 CI，镜像提供 arm64 清单也不能代替 ARM 实机测试。升级既有部署时注意：核心机密缺失会直接拒绝启动；DAG 不再绑定挂载，git pull 后要重建镜像；SFTP 连接必须配置 host_key。完整步骤见 部署教程。

    八、残余风险与路线图

    优先级事项影响建议
    P2Swarm 在多节点下的行为未验证CI 的演练只有一个节点：放置约束、节点故障后的重新调度、节点间的加密流量与共享存储都没有运行过；默认拓扑仍把所有服务固定在一台数据节点上扩展到多机前先配置共享存储，在两台主机上演练一次，并在节点之间放行 ESP（IP 协议 50）
    P2API 令牌经明文 HTTP 传输能读到流量的一方可以取得令牌；令牌是所有调用方共用的一个密钥保持回环绑定，经 SSH 隧道访问；对外暴露前在前面加终结 TLS 的网关
    P3容器阶段只在 CI 上运行本机没有 Docker，镜像、Compose 与 Swarm 的改动要推送之后才知道结果；失败原因与失败时的服务状态可以从公开注解读到，但错误注解这条路径还没有在真实的失败里用过每次推送后查看运行结果与注解；下一次出现失败的运行时核对注解是否足以定位；需要推送前验证时，在本机安装 Docker 或授权创建一个临时的 Docker 环境
    P3CSV 编码检查的两个限度检查要把输入多读一遍；编码指错但字节恰好合法时无法识别（没有字节序标记的 UTF-8 文本总是合法的 ISO-8859-1）。引号内的 CRLF 仍被存为 LF为数据源固定并写明编码；对结果有疑问时用 csv-profile 或抽样核对
    P2Spark 4.2.0 自带依赖的公告Spark 自带的 Jackson 2.21.2 在 OSV 中有 9 条公告（databind 6 条、core 3 条），Netty、Jetty 也有公告，当前配置下不可达；2026-10-09 复核时 Spark 仍只有 4.2.0不发布 Spark UI 与 RPC 端口；Spark 4.2.1 发布后升级
    P2机密在 Airflow 容器间共享任一任务代码都能读取全部机密，包括 JVM API 的令牌与 Redis 口令。只对任务隐藏其中几项意义不大：数据库口令与 Fernet 密钥足以改写元数据、解密连接视为可信代码边界；多租户前把 worker 与元数据库的凭据分开，再做机密隔离
    P3公告检查的覆盖范围每周的检查只看直接固定的 26 个版本，不含 Spark 与 Airflow 的传递依赖（例如 task-sdk），也不含基础镜像；基础镜像按标签拉取，没有固定 digest关注 Spark 与 Airflow 的发行说明；需要可重复的镜像时再固定 digest 并配套更新流程
    P3Airflow 上游的弃用提示Airflow 3.3.2 读取 .airflowignore 时，其自身代码触发 pathspec 1.1.1 的 DeprecationWarning，不影响行为；2026-10-09 复核时 3.3.2 仍是最新版等待 Airflow 上游修复；改用 regexp 忽略语法的收益不抵配置改动
    P3可选 Spark 镜像的 JDK可选的 datacraft/spark 镜像继承上游 apache/spark:4.2.0 的 JDK 25.0.3+9，低于 25.0.4.1（没有服务使用它）；上游镜像自 2026-07-16 以来没有更新上游 Spark 镜像更新后再重建；本机与运行镜像已是 25.0.4.1
