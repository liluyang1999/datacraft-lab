一、执行摘要

总体结论：datacraft-lab 已达到“个人单机数据处理平台可以放心使用和部署”的水平。CLI、HTTP API 与 Airflow 共用同一个 DataJob 契约和执行引擎，失败语义统一；8 个 Maven 模块按职责分为 core、io、processing、interfaces 四组，越界依赖在构建的 validate 阶段即失败；质量门禁不允许任何编译、类型检查或 Shell 检查警告，CI/CD 逻辑集中在 cicd/，可以脱离 GitHub Actions 在本机复现。

主要优势
  • 一个契约、一个引擎、三种入口，新作业注册一次即可在 CLI、API 与 Airflow 中使用（第三章）。
  • 模块边界、JDK 版本下限与零警告由构建强制，而不是靠约定（3.2、4.3）。
  • 262 项 JVM 测试与 99 项脚本、文档、DAG 测试，平台差异用标签表达，两个平台都没有跳过的测试（4.2）。
主要风险
  • HTTP API 没有认证，只能绑定回环地址或放在认证网关之后（第五章）。
  • Swarm 多机配置只做过静态与桩测试，不能当作高可用方案（第八章）。
  • GitHub Actions 额度不足，本轮改动没有在 Linux CI 上运行；需要 Docker 的镜像与 Compose 冒烟测试本轮未复验（4.5）。

云平台结论（第六章）：每月运行不足 227.5 小时时选 Oracle OCI A1 按需（60 小时约 $4.79/月）；常开或超过 227.5 小时选腾讯云 Lighthouse 入门型（$10.15/月）；必须使用 AWS 时选 Lightsail 8 GB（$44.15/月）。托管 Airflow 与 Cloudflare 运行时不采用，R2 只用于备份。所有价格为 2026-09-19 的公开价快照，尚未购买任何云资源。

本轮（2026-09-26）完成：工程目录按职责整理为 modules/、tests/、cicd/、docs/、design/；构建警告清零；JDK 25.0.4.1 成为强制下限；依赖逐项核对并同步到最新稳定版；本报告按“架构、质量、安全、云平台、风险”重新组织。逐项明细见附录 A。

除组合根外，每个模块的 POM 都有 Enforcer 规则 enforce-module-boundaries。负向检查已实际验证：给 datacraft-api 加入 datacraft-io 依赖，构建立即失败。
分组模块职责可依赖的项目模块

3.3 数据处理与数据根约束

  • 两类计算，各守其位：Spark 作业处理大文件，Spark 以 provided 作用域引入并由 spark-submit 提供，CLI 瘦 jar 因此只有约 9 MB；纯 JVM 作业处理小文件，不需要 Spark，可以在只含 JRE 的 API 镜像中运行。csv-profile 读取前检查文件大小（默认上限 64 MiB）与堆内存预算，超出时提示改用 Spark 的 row-count。
  • 数据根约束：设置 DATACRAFT_DATA_ROOT 后，纯 JVM 作业的输入必须严格位于数据根之内，并通过以数据根真实路径为根的 LocalStorageService 读取，拒绝指向根外的符号链接与目录联接；Spark 转换的输入输出同样受约束，并拒绝 glob 字符与输入输出重叠。API 镜像与部署栈中的 Airflow 服务都设置了数据根，API 以只读方式挂载数据卷。
  • 先校验、后启动：Spark 作业在启动会话之前完成参数校验，参数名只差大小写也会被拒绝；CSV 与 JSON 以 FAILFAST 方式读取，质量门槛（例如 expectedRows）不符即失败，不会静默退回默认值。
  • 边界：这是应用层防护，不是操作系统沙箱，硬链接和并发的恶意改动无法检测，数据根仍需要文件系统权限配合；row-count、spark-version、echo、noop 不受数据根约束。

3.4 部署拓扑

Swarm 模板：多机部署使用 CeleryExecutor 与 Redis，但所有服务都固定在 DATACRAFT_DATA_NODE 这一台数据节点上，因为数据卷是节点本地卷；API 不发布端口，只在覆盖网络内可达。在配置共享存储、加密覆盖网络与 Redis 认证之前，它不是高可用方案。

3.5 构建与 CI/CD 流水线

Maven 反应堆由根 POM 统一管理版本与质量门禁，./mvnw verify 依次执行 Enforcer（JDK 25.0.4.1 以上、Maven 3.9 以上、插件版本固定、禁止 POM 仓库、禁止有漏洞的 Jackson、模块边界）、编译（javac -Xlint:all 与 failOnWarning，scalac -Werror）、Spotless 与 Checkstyle、JUnit 与 ScalaTest，以及瘦 jar 打包。GitHub 只从 .github/workflows 读取工作流，因此 ci.yml 只负责触发条件、运行环境、固定版本的工具链与作业编排，每一步都调用 cicd/ 下的脚本或 tests/ 下的测试入口。

tests/ci/test_workflow.py 保证工作流里不再出现多行内联逻辑，工作流引用的脚本都存在，cicd/ 里的每个文件都有用途且没有被 git 忽略。

6.1 决策问题与约束

要回答的问题是：在用户指定的东京与新加坡两个地域，用哪家云平台运行本项目的单机栈最划算、风险最低。约束如下：

  • 工作负载：一台 Linux 主机运行 Docker Compose，内含 Airflow（LocalExecutor）、PostgreSQL、Spark local[2] 与 JVM API，默认只并发 1 个 Airflow 任务。规划起点为 8 GB 内存、至少 64 GB SSD；这是规划值，尚未用真实数据测出最低配置。
  • 两种用法：常开（按年均 730 小时/月计）与按需（约 60 小时/月，用完即停）。
  • 计价口径：2026-09-19 核验的税前公开价（美元），不计新用户赠金、限时促销、承诺折扣、税费、汇兑与人工；主机与磁盘保留整月；公网出站不超过 100 GB/月（含备份上传）；示例备份为 R2 Standard 上月均 20 GB，扣除账户免费 10 GB 后为 $0.15/月。
  • 完整价与下限：套餐价已包含磁盘、公网地址与流量的平台给出完整月费；EC2、GCP、Azure 与 Hetzner 的磁盘、公网地址、流量等取决于尚未确定的选项，只给出已知部分并标注“≥”，不把未核实的费用当作零。

    6.10 上线路径与验收条件

    从单机 Docker Compose 开始：并发 1 个 Airflow 任务、Spark local[2]、DAG 解析进程 1 个、API 服务器 worker 1 个。

    python3 deploy/scripts/deployment_env.py init   # 生成独立随机机密，不覆盖已有文件
bash deploy/scripts/build-images.sh              # 拉取基础镜像并构建（DAG 与 jar 均打入镜像）
bash deploy/scripts/compose-up.sh                # 预检机密与端口后启动并等待健康

    购买前须完成的验收：

    1. 在目标账户与地域确认可售库存和实际报价（腾讯云国际站；OCI 主区域的 A1 容量）。
    2. 从数据源所在网络分别测试到东京与新加坡的延迟与下载速度，按数据源位置选择地域。
    3. 选 OCI 时，在 arm64 主机上构建镜像并运行容器冒烟测试，确认镜像与 Spark 作业可用。
    4. 用真实数据量运行三条 DAG，记录峰值内存、磁盘占用与任务耗时，确认 8 GB / 64 GB 的规划足够；按需方案用实测耗时重算交点。
    5. 完成一次备份与恢复演练：pg_dump 到 R2，再恢复到独立数据库。
    6. 主机只开放受限 SSH；应用端口保持回环绑定；机密由 deployment_env.py init 生成。
    验收边界

    部署脚本已经就绪，但没有购买或上线任何云资源。真实云账号权限、库存、网络延迟、用户数据下的性能与 ARM 主机运行都未验证；当前容器运行证据来自 Linux amd64 的 CI，镜像提供 arm64 清单也不能代替 ARM 实机测试。升级既有部署时注意：核心机密缺失会直接拒绝启动；DAG 不再绑定挂载，git pull 后要重建镜像；SFTP 连接必须配置 host_key。完整步骤见 部署教程。

    P1API 无认证误暴露即可被任意调用保持回环绑定；需要远程访问时在前面加认证网关
    P1Swarm 未在真实多节点验证初始化服务、健康检查与节点排空只做过静态与桩测试扩展到多机前先配置共享存储、加密覆盖网络与 Redis 认证，并做一次演练
    P2本轮 CI 未运行镜像构建、容器与 Compose 冒烟、Stack 文件校验以及新的工作流本身没有在 Linux 上执行过额度恢复后手动触发一次 workflow_dispatch；在此之前以本机验证为准
    P2Spark 4.2.0 自带依赖的公告Jackson 2.21.2、Netty、Jetty 有公告，当前配置下不可达不发布 Spark UI 与 RPC 端口；Spark 4.2.1 发布后升级
    P2机密在 Airflow 容器间共享任一任务代码都能读取全部机密视为可信代码边界；多租户前再做机密隔离
    P2无持续依赖与漏洞监控固定 SHA 的 Actions 与依赖会逐渐过时经所有者同意后启用 Dependabot 与定期 SCA 扫描；基础镜像固定 digest
    P3Airflow 上游的弃用提示Airflow 3.3.2 读取 .airflowignore 时，其自身代码触发 pathspec 1.1.1 的 DeprecationWarning，不影响行为等待 Airflow 上游修复；改用 regexp 忽略语法的收益不抵配置改动
    P3可选 Spark 镜像的 JDK可选的 datacraft/spark 镜像继承上游 apache/spark:4.2.0 的 JDK 25.0.3+9，低于 25.0.4.1（没有服务使用它）上游 Spark 镜像更新后再重建；本机与运行镜像已是 25.0.4.1
    P3Spark 会话锁无超时；durationMillis 含排队时间；Lifecycle 仅为标签当前部署拓扑下不触发引入 HTTP 侧 Spark 服务或多租户时再处理
    路线图功能扩展—更多纯 JVM 作业与流式 CSV 解析；配置化作业目录；对象存储版 StorageService（S3A）；docker secrets；云端、ARM 与真实 SFTP 服务器验收
