一、结论摘要

总体判断：项目已达到“个人单机数据处理平台可以放心使用和部署”的水平。CLI、HTTP API 与 Airflow 共用同一个 DataJob 契约和执行引擎；8 个 Maven 模块按职责分成 core、io、processing、interfaces 四组，每个模块可以依赖哪些项目模块由构建强制检查；CI/CD 流水线逻辑集中在 cicd/，覆盖构建、真实 Spark、真实 Airflow 流水线、镜像与 Compose 栈，并且可以脱离 GitHub Actions 在本机运行。

本轮（2026-09-26）完成的工作：

  • 工程目录按职责重组。源码模块移入 modules/ 的四个分组，全部测试移入 tests/，CI/CD 逻辑集中到 cicd/，文档集中到 docs/，架构设计集中到 design/。artifactId 与包名不变，文件移动保留 git 历史。
  • CI/CD 逻辑独立。GitHub 只从 .github/workflows 读取工作流，所以 ci.yml 留在原处，但只负责触发条件、运行环境和作业编排；原来写在 YAML 里的检查全部改为 cicd/ 下按作业分组的脚本（build、airflow、lint、stacks），并有测试保证工作流不再出现多行内联逻辑。
  • 告警清零并设门禁。javac -Xlint:all 加 failOnWarning、scalac -Werror、pyright 0 诊断（已加入 CI）；shade 不再报告资源重叠；测试日志默认静默；平台相关测试改为按标签排除，Windows 与 Linux 都不再出现跳过或取消。ShellCheck 门禁从 error 收紧到 warning 级别。本机 JDK 升级到 25.0.4.1 后，完整构建的输出从 6,715 行降到 623 行，[WARNING] 与 JVM 警告从 32 条降到 0 条。
  • 依赖与代码同步到最新。逐项对照 Maven Central、PyPI、npm、Docker Hub 与 GitHub：升级 6 个构建与测试组件，pyright 固定到最新的 1.1.414，CI 升到 Node 24 与 Python 3.13；JDK 下限改为强制要求 25.0.4.1（本机、CI 与构建镜像均已是该版本），其余均已是最新稳定版。Jackson 3 因 Spark 4.2 固定使用 Jackson 2 而不迁移。
  • 云平台抉择定稿。常开选腾讯云 Lighthouse 入门型（$10.15/月）；每月约 60 小时选 Oracle OCI A1（$4.79/月）；必须使用 AWS 时选 Lightsail 8 GB（$44.15/月）。托管 Airflow 与 Cloudflare 运行时不采用，R2 只存备份。

仍需注意（详见第九节）：API 没有认证，只能留在回环地址或放在认证网关之后；Swarm 多机配置只做过静态与桩测试；Spark 4.2.0 自带依赖有当前不可达的安全公告；GitHub Actions 额度不足，本轮推送不会触发 CI，Docker 镜像、Compose 栈与 Stack 文件校验本轮没有在 Linux 上重新运行（见第六节）。

三、架构与模块职责

3.1 执行主干

HTTP (datacraft-api)      CLI (datacraft-cli)      Airflow DAG (BashOperator)
        \                        |                         /
         \                       |      java -jar / spark-submit --class Runner
          +------------> JobExecutionEngine (datacraft-engine) <--------+
                                 |  catalog = JvmJobs + SparkJobs + BuiltInJobs
             +-------------------+----------------------+
             |                   |                      |
     BuiltInJobs [engine]   JvmJobs [jobs]        SparkJobs [spark]
      echo, noop            csv-profile,           spark-version,
                            file-checksum          csv-to-parquet, row-count
                                 |
                        datacraft-io (StorageService, CsvFiles, SFTP)

“一个契约、一个引擎、多种入口”是本项目最大的优点：新作业只需实现 DataJob 并注册，就能同时在 CLI、API 与 Airflow 中使用。引擎对所有非虚拟机级错误给出统一的 FAILED 结果；作业名必须是单个 URL 路径段，且不能与 CLI 控制命令同名；Spark 作业在纯 JVM 环境中返回带 spark-submit 提示的失败结果，而不是崩溃。

3.2 模块职责与依赖范围

除组合根 datacraft-cli 外，每个模块的 POM 都有 Enforcer 规则 enforce-module-boundaries：依赖了允许范围之外的项目模块（或在非 Spark 模块中引入 Spark）会使 validate 阶段失败。负向检查已验证：给 datacraft-api 加入 datacraft-io 依赖，构建立即失败并指向设计文档。

    8.6 不采用的方案

    方案不采用的原因
    AWS MWAA、Google 托管 Airflow常驻环境要计控制面、工作节点、数据库与网络费用；MWAA Serverless 另按任务计费，但现有本地 JVM/Spark 命令与其托管任务模型不直接兼容。当前规模没有证明迁移与维护成本值得。
    Cloudflare Workers / Pages / ContainersWorkers/Pages 不能运行 JVM + PostgreSQL + Airflow；Containers 能运行 Linux 容器，但生命周期与存储模型需要重新适配，不是现有有状态栈的直接替换。项目未配置 S3A，s3:// 路径不算已支持的 Spark 数据路径。
    Savings Plans、Reserved Instances、CUD先观察稳定利用率；承诺费不会因为偶尔关机而消失。
    多机 Swarm 高可用默认 Swarm 使用本地卷并固定数据节点，仍不是多主机高可用；需要共享存储、加密覆盖网络与 Redis 认证后再考虑。
