# 1.0.0：版本、安装包、CI/CD、设计基线与实时监控（2026-11-20）

从干净的 `bac810f` 开始。本轮按用户要求，把版本号管理、构建与打包、Windows 安装与卸载、CI/CD
对齐 datachain-ark 的设计理念，版本从 1.0.0 开始；把界面设计收进 `design/ui` 作为唯一基线并打磨；
新增能实时获取后台信息的监控视图；随后查缺补漏、验证、清理并同步文档。沿用既有的模块边界、公开作业名、
数据库结构与命名惯例。

## 起点

改动前的基线在本机 Windows 上全部通过：后端 `verify` 329 项、桌面 `verify` 183 项，0 警告。
基线截图显示的可打磨处：侧栏只有文字字标且带英文名 DataCraft；总览三块信息块宽度不等、右侧留白，
块内是有边框的“连接详情”按钮；`base.css` 有不在字号阶梯上的 14、17、22 px 与 3、5、17 px 内边距；
颜色在两个主题文件和界面设计文档的表格里各写一份。`ConnectionMonitor` 已记录延迟历史，但没有界面使用。

## 改动

| 范围 | 结果 |
| --- | --- |
| 版本 | 根 `pom.xml` 的 `revision`（1.0.0）是唯一版本字面值；八个模块与桌面继承 `${revision}`。命令行用法首行、引擎 `GET /status`、桌面侧栏与“关于”读构建过滤的 `version.properties`；打包、安装器与 CI 读 `cicd/release/version.py`。[版本管理](../versioning.md)列出全部消费方，`test_versioning.py` 拒绝第二个字面值。[CHANGELOG](../CHANGELOG.md) 改为按版本记录，1.0.0 之前的开发记录原样保留在后面 |
| 引擎 API | 新增需令牌的只读 `GET|HEAD /status`：版本、启动时刻与已运行时长、作业数、并发上限、正在运行的作业（只有作业名与时间，不含参数）以及自启动以来开始、成功、失败、被拒绝的运行数。`/health` 不变 |
| 监控视图 | 新增第六个视图“监控”（Ctrl+4）：需要关注的提醒（后台不可达或认证失败、状态异常、DAG 文件无法解析、资源池满且有任务在等、任务等待重试、引擎最近 10 分钟拒绝运行），引擎负载与计数、Airflow 各组件心跳，两个后台最近 120 次检查的延迟折线与可用率，所有 DAG 正在运行或等待的任务，资源池槽位，DAG 导入错误。侧栏显示提醒数量。可见时每 5 s、后台每 60 s、最小化时停止；各部分独立成败 |
| 桌面其他 | 侧栏标志（应用图标的运行纹带）加名称与版本，药丸形导航；总览三块等宽，详情改为角落的 ⓘ；设置新增“关于”；同一数据目录只运行一个进程，再次启动唤回窗口；运行中的应用持有安装程序检测的互斥体 |
| 设计基线 | `design/ui/tokens.json` 是颜色、字号、圆角、间距与时长的唯一来源，`build.py` 生成桌面 `light.css`、`dark.css` 与原型的 `tokens.css`，`--check` 同时把 `base.css` 卡在刻度上（修正了上面的偏差）。[原型](../../design/ui/index.html)可浏览六个视图 × 三种状态 × 两个主题 × 两种宽度；[规格](../../design/ui/SPEC.md)由原界面设计文档迁入并更新，不再复制颜色值 |
| 安装包 | 根目录 `build.bat` 依次运行干净的桌面打包、`package_desktop.py`（应用目录 `DatacraftLab`、AOT、20 次计时启动）与 `build_installer.py`，生成 `dist/Setup.exe` 与 SHA-256；`run.bat` 从源码启动。Inno Setup 机器级安装：中文向导，默认 `C:\Program Files\DatacraftLab` 或自选空文件夹，开始菜单与“已安装的应用”名称为“数艺工坊”；同版本修复，拒绝降级，拒绝写入有他人文件的目录，应用运行时拒绝安装与卸载；卸载保留 `~/.datacraft` |
| CI/CD | `ci.yml` 与 `advisories.yml` 换成唯一入口 `cicd.yml` 加 `check`、`test`、`build`、`deploy` 四个可复用阶段：推送与合并请求依次运行前三个，周一定时只运行 check，`main` 上手动填写版本号才进入 deploy（先核对分支、版本与标签；发布渠道未定，只汇总不发布）。build 阶段在 Windows 上从 `build.bat` 构建安装包并走完整生命周期 |
| 决策 | [决策 15–18](../../design/decisions.md#15-one-product-version-written-once-as-the-root-poms-revision)记录单一版本、分阶段 CI/CD、安装器与设计令牌 |

## 查缺补漏

- 界面测试发现 `Meter` 在第一次取得数据前布局时抛出 `NoSuchElementException`；改为构造时就有空轨道并在无图形时跳过布局。
- 截图发现侧栏为监控项加计数时把“活动”项挤掉：先把容器放进原位置再移入导航项，`ShellContentTest` 新增回归。
- 延迟只有一次检查时折线区域看似空白：加入基线、最新一点的空心圆，并在最慢一次之上留 25% 余量。
- `SettingsModelTest` 的一次失败来自既有竞态：连接监视器的后台健康检查与测试共用桩服务器的请求计数。
  该测试改用独立桩服务器后连续三次通过。
- 首次 `build.bat` 因 `target` 中残留的 `0.1.0-SNAPSHOT` jar 停止；发布构建改为 `clean package`，锁文件移出 `target`。
- 清理：删除本轮新增但无人使用的 `MonitorService.engineVersion()`、`Status.load()`、`Pool.used()`、
  `Sparkline.capacity()`，以及此前已无人使用的 `MONITOR` 图标。

## 边界

- 远端 CI 尚未运行：新的工作流、Windows 安装包作业与机器级生命周期（含运行中拒绝安装）只有推送后才有证据。
- 安装包未做代码签名；公开分发前需要证书，否则 SmartScreen 会提示。
- deploy 阶段是占位：发布渠道、`release` 环境的审批人与 `v1.0.0` 标签尚未配置。
- 监控视图的 Airflow 接口（导入错误、资源池、跨 DAG 的任务实例）按 3.3.2 的 OpenAPI 定义实现，并由桩服务器测试；
  本轮没有对真实 Airflow 做端到端验收。
- 原型截图因应用窗口隐藏而超时，原型的检查以 DOM 测量完成，桌面外观以门禁截图核对。
- `develop` 分支的触发已写入入口，但仓库目前只有 `main`；是否采用 develop / main 的合并流程由用户决定。
