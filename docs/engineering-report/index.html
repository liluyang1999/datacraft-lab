一、工程定位

本工程定位为个人数据处理在线通用引擎中心。核心目标不是把所有能力堆入一个入口类，而是建立清晰的端口、 抽象、实现和适配层，让本地批处理、Spark 作业、HTTP 在线调用和 Airflow 编排都能复用同一套作业执行语义。

当前工程采用保守的标准 JVM 结构：父 POM 统一管理版本和质量插件，子模块只声明自身依赖和模块级打包配置。 Java 用于稳定的领域端口、基础设施实现和不依赖 Spark 的 JVM 作业，Scala 用于 CLI、Spark 作业和更自然的数据处理入口。

二、模块总览

模块 包名 职责 关键类型
datacraft-common com.example.datacraft.common 跨模块基础模型，不依赖任何业务或基础设施模块。 Lifecycle, DataCraftException, AppInfo
datacraft-config com.example.datacraft.config 配置加载和类型读取，隔离配置来源和消费方。 DataCraftConfig
datacraft-io com.example.datacraft.io 本地文件、根目录约束存储端口、小文件 CSV 读写、SFTP 传输。 StorageService, LocalStorageService, LocalFiles, CsvFiles, SftpClient
datacraft-engine com.example.datacraft.engine 作业契约、作业目录、执行请求与执行结果，是在线/离线复用的中心层；内置 echo、noop 两个作业。 DataJob, JobCatalog, JobRegistry, JobExecutionEngine, BuiltInJobs
datacraft-jobs com.example.datacraft.jobs 不需要 Spark 运行时的 JVM 小文件数据作业 csv-profile 与 file-checksum，沿用 DataJob 契约并复用 datacraft-io；设置 DATACRAFT_DATA_ROOT 时输入文件必须位于该目录内。 JvmJobs, CsvProfileJob, FileChecksumJob, InputFiles
datacraft-spark com.example.datacraft.spark Spark 运行配置、Session 生命周期、可复用 DataFrame 读写，以及把 Spark 作业桥接到引擎 DataJob 契约。 SparkRuntimeConfig, SparkSessions, DataFrames, AbstractSparkDataJob, SparkJobs
datacraft-api com.example.datacraft.api 轻量 HTTP 在线入口，调用引擎层，不持有业务逻辑。 EngineHttpServer, EngineJson, HttpJsonResponse
datacraft-cli com.example.datacraft.cli 命令行入口，供本地用户、脚本和 Airflow 调用；组装完整作业目录并打包为可执行 shaded jar。 Runner, CliParser, CommandLineArgs

三、依赖方向

模块依赖必须单向、清晰、可解释。下面列出各模块 pom.xml 声明的直接依赖（不含测试依赖）： 箭头后为项目内模块，“外部”为第三方构件。 

datacraft-common   -> （无项目内依赖）
datacraft-config   -> common
datacraft-io       -> common                        外部：jsch
datacraft-engine   -> common                        Enforcer 限定：仅 common，禁止 Spark
datacraft-jobs     -> common, engine, io
datacraft-spark    -> common, engine                外部：scala-library、Spark（spark.scope，默认 provided）
datacraft-api      -> common, engine                外部：jackson-databind
datacraft-cli      -> common, config, api, engine, io, jobs, spark    外部：scala-library、scopt

orchestration/airflow
  -> 调用 datacraft-cli 构建产物（java -jar / spark-submit）

datacraft-engine 的 enforce-module-boundaries 规则在项目模块中只允许它依赖 datacraft-common，并禁止任何 Spark 构件，违反时构建在 validate 阶段失败；其他模块都直接依赖 common，common 若反向依赖上层模块会形成环， 由 Maven reactor 的循环检测拒绝。禁止 API 或 CLI 持有具体业务实现。

四、核心抽象说明

1. 存储端口

StorageService 是应用层访问文件系统的稳定端口。它不暴露绝对路径，避免上层代码绕过根目录约束。 LocalStorageService 是根目录绑定实现，所有路径都必须是相对路径，并且不能通过 .. 逃逸根目录； 路径穿过符号链接，或任一已存在路径段的真实位置落在根目录之外（例如 Windows junction）时同样拒绝。 它是应用层防护而不是操作系统沙箱：硬链接、Windows 保留设备名（如 NUL）和并发文件系统变更不在检测范围内。

LocalFiles 保留为低层 NIO 工具，不承担领域边界。这个分层避免了“工具函数直接散落到业务代码”。

2. 作业目录端口

JobCatalog 是只读作业目录端口，定义作业查询、列举和必需作业读取语义。 JobRegistry 是当前内存实现，负责注册、名称校验（拒绝空名、重复名和含 / 的名称）和按名称稳定排序。

JobExecutionEngine 只依赖 JobCatalog，不绑定具体注册表。后续如果切换为数据库目录、 配置文件目录或插件扫描目录，不需要改执行引擎。

3. HTTP 在线入口

EngineHttpServer 只负责 HTTP 路由和执行流程协调。 EngineJson 负责引擎响应 JSON 编码，HttpJsonResponse 负责 HTTP 响应写入。 这个拆分避免服务器类同时承担路由、序列化和响应 I/O 三种职责。

API 没有认证，且文件作业会读取 input 指定的路径，因此 serve-api 在 --host 不是回环地址且 DATACRAFT_DATA_ROOT 未设置或为空白时拒绝启动（退出码 2）。

4. Spark 运行抽象

SparkRuntimeConfig 描述 Spark 本地或集群运行参数。master 依次取作业参数 spark.master、 spark-submit --master，都没有时使用 local[*]，即在没有集群时使用本机多核心运行。 SparkSessions 是 SparkSession 工厂和释放入口。

5. JVM 数据作业

JvmJobs.register 把 csv-profile 与 file-checksum 注册进同一个 JobRegistry，与内置作业和 Spark 作业共用一个目录，在 CLI 和 HTTP API 中都可运行，只需普通 java -jar，不需要 Spark 运行时。InputFiles 在设置了 DATACRAFT_DATA_ROOT （去除首尾空白后非空）时要求输入规范化后严格位于该目录内，并只经 LocalStorageService 读取； 未设置时直接用 LocalFiles 读取任意可读路径。

五、运行路径

CLI 执行作业

java -jar datacraft-cli/target/datacraft-cli.jar --command echo --param message=hello

Runner
  -> CliParser
  -> Runner.registry()
       = requireDispatchable(JvmJobs.register(SparkJobs.register(BuiltInJobs.registry())))
  -> JobExecutionEngine
  -> DataJob.run()
  -> JobExecutionResult

HTTP 在线执行

POST /jobs/echo/runs?lifecycle=dev&message=hello

EngineHttpServer
  -> 方法检查（非 POST 返回 405）与 Origin 检查（带 Origin 返回 403）
  -> parseQuery()
  -> JobExecutionRequest
  -> JobExecutionEngine
  -> EngineJson.result()
  -> HttpJsonResponse.write()（SUCCEEDED 返回 200，FAILED 返回 500）

Airflow 编排

构建阶段 Maven package -> 部署 datacraft-cli.jar
Airflow DAG
  -> 普通作业 java -jar / Spark 作业 spark-submit
  -> 复用 CLI 和 engine 能力
  -> JSON 结果经 XCom 传递，row-count 校验转换行数

六、API 端点

方法 路径 说明
GET | HEAD /health 服务健康检查。
GET | HEAD /jobs 列出当前作业目录中的作业名称和描述。
POST /jobs/{jobName}/runs?lifecycle=dev&key=value 同步触发一个作业，查询参数会进入 JobExecutionRequest.parameters。

运行请求 SUCCEEDED 返回 200、FAILED（包括作业参数校验失败）返回 500，两者都带结果 JSON； 格式错误的请求返回 400 invalid_request（java.net.URI 无法解析的请求目标在进入处理器前 由 JDK 直接返回 HTML 400）；带 Origin 头的运行请求返回 403 cross_origin_forbidden； 未知路由和作业返回 JSON 404；方法不符返回 405 并带 Allow 头。完整状态约定见 数据处理契约。

七、开发规范

  • 新增跨模块模型优先放入 datacraft-common，但 common 不允许依赖上层模块。
  • 新增 IO 能力优先通过 StorageService 表达应用需求，再决定是否补充底层 LocalFiles 能力。
  • 新增可执行任务必须实现 DataJob，并通过 JobCatalog 暴露给 CLI/API。
  • 作业名不得包含 /，也不得与 CLI 控制命令 list-jobs、serve-api 重名。
  • 不依赖 Spark 的 JVM 数据作业放入 datacraft-jobs，并通过 JvmJobs 注册。
  • 新增 Spark 作业应保持 Spark 相关代码在 datacraft-spark 或未来 Spark 业务模块内。
  • API 层不得直接写业务逻辑，只负责协议适配、请求转换和响应编码。
  • CLI 层不得复制 API 或 engine 逻辑，只做参数解析和入口编排。

# Linux / macOS / WSL，与 CI 相同

当前工程以 Java 25 字节码为目标构建（Spark 4.2.0 / Scala 2.13.18）。Enforcer 要求 JDK 25 及以上， 低于 25.0.3 时输出警告并继续构建。Windows 本机如果没有全局设置 JAVA_HOME，需要在 PowerShell 会话内显式设置。 CI 在 ubuntu-24.04 上执行 ./mvnw -B -ntp verify，以其结果为准。

九、扩展建议

  • datacraft-jobs 模块已建立（csv-profile、file-checksum）；后续不依赖 Spark 的 JVM 数据作业继续放在该模块，并沿用 DATACRAFT_DATA_ROOT 路径约束。
  • 当 HTTP API 面稳定后，再考虑引入成熟 Web 框架；当前 JDK HTTP server 更适合底座阶段。
  • 当作业数量增多后，可新增插件扫描或配置驱动的 JobCatalog 实现。
  • 当需要对象存储、HDFS 或云存储时，新增 StorageService 实现，而不是修改业务作业。
  • 新增 Airflow DAG 复用 datacraft_common.py 的参数、超时、重试与结果约定，并加入真实 DAG 测试。
