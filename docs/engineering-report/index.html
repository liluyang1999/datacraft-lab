datacraft-lab 工程开发文档

Maven 多模块、Java/Scala 混合、Spark 本地执行、Airflow 编排与在线引擎中心的标准工程说明。

父项目 datacraft-lab
基础包名 com.example.datacraft
构建体系 Maven Wrapper + 多模块 Reactor
质量门 Spotless、Scalafmt、google-java-format、Checkstyle、Maven Enforcer、JUnit、ScalaTest

一、工程定位

本工程定位为个人数据处理在线通用引擎中心。核心目标不是把所有能力堆入一个入口类，而是建立清晰的端口、 抽象、实现和适配层，让本地批处理、Spark 作业、HTTP 在线调用和 Airflow 编排都能复用同一套作业执行语义。

当前工程采用保守的标准 JVM 结构：父 POM 统一管理版本和质量插件，子模块只声明自身依赖和模块级打包配置。 Java 用于稳定的领域端口和基础设施实现，Scala 用于 CLI、Spark 作业和更自然的数据处理入口。

二、模块总览

模块 包名 职责 关键类型
datacraft-common com.example.datacraft.common 跨模块基础模型，不依赖任何业务或基础设施模块。 Lifecycle, DataCraftException, AppInfo
datacraft-config com.example.datacraft.config 配置加载和类型读取，隔离配置来源和消费方。 DataCraftConfig
datacraft-io com.example.datacraft.io 本地文件、根目录约束存储端口、SFTP 传输。 StorageService, LocalStorageService, LocalFiles, SftpClient
datacraft-engine com.example.datacraft.engine 作业契约、作业目录、执行请求与执行结果，是在线/离线复用的中心层。 DataJob, JobCatalog, JobRegistry, JobExecutionEngine
datacraft-spark com.example.datacraft.spark Spark 运行配置、Session 生命周期、可复用 DataFrame 读写，以及把 Spark 作业桥接到引擎 DataJob 契约。 SparkRuntimeConfig, SparkSessions, DataFrames, AbstractSparkDataJob, SparkJobs
datacraft-api com.example.datacraft.api 轻量 HTTP 在线入口，调用引擎层，不持有业务逻辑。 EngineHttpServer, EngineJson, HttpJsonResponse
datacraft-cli com.example.datacraft.cli 命令行入口，供本地用户、脚本和 Airflow 调用。 Runner, CliParser, CommandLineArgs

三、依赖方向

模块依赖必须单向、清晰、可解释。当前推荐依赖方向如下：

datacraft-common
  -> datacraft-config
  -> datacraft-io
  -> datacraft-engine
  -> datacraft-spark
  -> datacraft-api
  -> datacraft-cli

orchestration/airflow
  -> 调用 datacraft-cli 构建产物

实际 Maven 依赖不是简单链式，而是按职责声明。例如 API 依赖 engine，CLI 依赖 api、engine、io、spark。 禁止 common 反向依赖上层模块，禁止 API 或 CLI 持有具体业务实现。

四、核心抽象说明

1. 存储端口

StorageService 是应用层访问文件系统的稳定端口。它不暴露绝对路径，避免上层代码绕过根目录约束。 LocalStorageService 是根目录绑定实现，所有路径都必须是相对路径，并且不能通过 .. 逃逸根目录。

LocalFiles 保留为低层 NIO 工具，不承担领域边界。这个分层避免了“工具函数直接散落到业务代码”。

2. 作业目录端口

JobCatalog 是只读作业目录端口，定义作业查询、列举和必需作业读取语义。 JobRegistry 是当前内存实现，负责注册、重复名称校验和稳定排序。

JobExecutionEngine 只依赖 JobCatalog，不绑定具体注册表。后续如果切换为数据库目录、 配置文件目录或插件扫描目录，不需要改执行引擎。

3. HTTP 在线入口

EngineHttpServer 只负责 HTTP 路由和执行流程协调。 EngineJson 负责引擎响应 JSON 编码，HttpJsonResponse 负责 HTTP 响应写入。 这个拆分避免服务器类同时承担路由、序列化和响应 I/O 三种职责。

4. Spark 运行抽象

SparkRuntimeConfig 描述 Spark 本地或集群运行参数。默认 master 是 local[*]， 适合在没有集群时使用本机多核心运行。SparkSessions 是 SparkSession 工厂和释放入口。

五、运行路径

CLI 执行内置作业

java -jar datacraft-cli/target/datacraft-cli.jar --command echo --param message=hello

Runner
  -> CliParser
  -> BuiltInJobs.registry()
  -> JobExecutionEngine
  -> DataJob.run()
  -> JobExecutionResult

HTTP 在线执行

POST /jobs/echo/runs?lifecycle=dev&message=hello

EngineHttpServer
  -> parseQuery()
  -> JobExecutionRequest
  -> JobExecutionEngine
  -> EngineJson.result()
  -> HttpJsonResponse.write()

Airflow 编排

Airflow DAG
  -> Maven package
  -> java -jar datacraft-cli.jar --command ...
  -> 复用 CLI 和 engine 能力

六、API 端点

方法 路径 说明
GET /health 服务健康检查。
GET /jobs 列出当前作业目录中的作业名称和描述。
POST /jobs/{jobName}/runs?lifecycle=dev&key=value 同步触发一个作业，查询参数会进入 JobExecutionRequest.parameters。

七、开发规范

  • 新增跨模块模型优先放入 datacraft-common，但 common 不允许依赖上层模块。
  • 新增 IO 能力优先通过 StorageService 表达应用需求，再决定是否补充底层 LocalFiles 能力。
  • 新增可执行任务必须实现 DataJob，并通过 JobCatalog 暴露给 CLI/API。
  • 新增 Spark 作业应保持 Spark 相关代码在 datacraft-spark 或未来 Spark 业务模块内。
  • API 层不得直接写业务逻辑，只负责协议适配、请求转换和响应编码。
  • CLI 层不得复制 API 或 engine 逻辑，只做参数解析和入口编排。

八、质量门与验证

父 POM 统一管理所有依赖版本和插件版本，当前质量门包括：

Maven Enforcer Spotless Scalafmt google-java-format Checkstyle JUnit Jupiter ScalaTest 

$env:JAVA_HOME='D:\Java'
.\mvnw.cmd verify

当前工程在 JDK 21 字节码目标下构建。Windows 本机如果没有全局设置 JAVA_HOME， 需要在 PowerShell 会话内显式设置。

Maven 构建体系的完整布局、插件职责、生命周期绑定和生产命令详见 Maven 构建配置专题报告。

九、扩展建议

  • 下一步可新增 datacraft-jobs 模块，集中放置实际数据处理作业。
  • 当 HTTP API 面稳定后，再考虑引入成熟 Web 框架；当前 JDK HTTP server 更适合底座阶段。
  • 当作业数量增多后，可新增插件扫描或配置驱动的 JobCatalog 实现。
  • 当需要对象存储、HDFS 或云存储时，新增 StorageService 实现，而不是修改业务作业。
  • 当 Airflow DAG 增多后，可在 orchestration/airflow 内增加统一模板和环境变量规范。
