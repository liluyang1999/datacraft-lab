没有丢弃首次或较慢样本。Windows 使用一级 JIT，Linux 保留默认分层编译，原因见下方“手段”。

完整样本及失败历史记在 [L8](loop/log.md#l8-启动与原生无障碍专项2026-10-28)。

上一提交的共享 Windows runner 曾有 2074 / 1929 ms 早期尖峰，严格门禁失败；新增阶段与 CPU 诊断
没有被当作性能修复。当前样本通过也不能证明此前尖峰的具体系统成因已经消除，后续仍执行相同严格预算。
本轮较慢的 927 ms 样本与 559 ms 样本只相差 63 ms 进程 CPU，更符合等待或调度波动，
但尚不能据此指认具体系统组件。固定机器的本机验收和共享 CI 分别列示，不能互相替代。

| 指标 | 目标 | 本轮证据与边界 |
| --- | --- | --- |
| 视图切换 | ≤ 100 ms，首次 ≤ 200 ms | Windows 116、Linux 114 项门禁通过；每页真实绘制后才计作预热，首次绘制另受 200 ms watchdog 约束 |

| 操作反馈 | ≤ 100 ms | 首次 HTTP/TLS 初始化在后台，取消、超时、关闭不会留下迟发请求；五项同步回归通过 |
| 内存 | 常驻 ≤ 250 MB | 保留 32/256 MiB 堆；188.1 MiB 工作集、375.7 MiB 私有提交为 L7 空状态历史抽样，本轮没有重做长期内存测量 |

阶段定位发现，尚未连接后台时也会提前创建 HTTP 客户端及 TLS，Linux 服务准备常比工具包晚约 100 ms。
改为首次请求时在后台共享初始化后，不再阻挡首屏。初始化等待仍计入请求总时限，过期请求不会迟发。
此前一版 Linux 的 20 个样本中有 1529 ms，门禁确实失败；该失败与最终全部样本保留在 L8，未提高阈值。
GC 交替对照没有稳定收益，因此没有修改 GC。软件渲染虽减少启动耗时，却在完整界面测试中内存不足，已撤回。
L7 的 1.314–3.283 s 等历史结果和负载条件保留在 [L7 记录](loop/log.md#l7-全面复核与边界打磨2026-10-28)。

启动优化的历史分解（2026-10-27，不带 AOT 缓存，改进前 → 改进后；不替代上方本轮结果）：

| 阶段 | 改进前 | 改进后 |
| --- | --- | --- |
| JVM 与 JavaFX 工具包启动 | 约 1.0 s | 约 0.9 s，与下一行并行 |
| 打开 SQLite（加载本机库）、DPAPI、HTTP 客户端（TLS 初始化）、JSON | 约 0.7 s，在工具包之后串行 | 在启动器里另起线程，与工具包启动并行 |
| 构建窗口（控件类加载、默认样式表、主题、第一个视图） | 约 0.55 s，含窗口图标 75 ms | 约 0.5 s；窗口图标改到首帧之后绘制 |
| 首次布局与渲染 | 约 0.3 s | 约 0.3 s |
| 合计到首帧 | 约 2.55 s | 约 1.7 s；带 AOT 缓存约 1.1 s |

AOT 缓存（JDK 25 的 JEP 483/514）记录启动时加载与链接的类，省去余下的大部分类加载。它只认 jar 组成的类路径，
所以由打包脚本生成（见 [README](README.md#打包)），`javafx:run` 从 `target/classes` 目录运行，不能使用。

## 手段

- **FX 线程只做界面：**网络、SQLite、JSON、加解密全部在后台；轮询的到点线程不读界面的列表与属性，
  只读后台线程可见的 `volatile` 副本。
- **就地更新：**轮询结果按主键与当前列表比较，只替换变化的元素（`Lists.reconcile`），表格不重建、
  不闪烁、不丢失选中与滚动位置；短列表（总览）只更新变化的行（`Rows`）。
- **合并更新：**同一轮询的新结果覆盖尚未应用的旧结果（`Latest`）；交付时再次检查代次，停止前排队的结果不再应用。
- **固定行高：**表格与列表设 `-fx-fixed-cell-size`，虚拟化只计算可见行。
- **少用特效：**阴影只用在通知、侧滑面板、菜单与提示，表格单元格里没有效果与渐变；侧栏开启缓存。
  侧滑面板的阴影绘在独立的静态底板上，日志滚动不重新模糊整块面板与其中的文字。
- **懒加载：**视图首次打开才创建，日志按段读取，侧滑面板关闭后释放内容与监听器。
- **堆边界：**打包与测试均使用 `-Xms32m -Xmx256m`，避免初始堆随主机内存扩大；同样的五视图空状态抽样中，
  调整前主进程工作集 248.9 MiB、私有提交 890.4 MiB。堆上限不是进程总内存上限，JavaFX 与本机库另占内存。
- **桌面编译策略：**Windows 的桌面包、测试及开发启动使用 `-XX:TieredStopAtLevel=1`，降低启动时 JIT 编译竞争。
  同机交替六次的默认策略中位数 / 最大为 1271 / 1424 ms，一级编译为 1127 / 1190 ms。
  代价是不使用 C2 的长期吞吐优化，因此只用于 Windows 的有界客户端；Linux 保留默认四级编译，
  避免限制软件渲染吞吐。引擎、Spark 与 API 进程保持原策略。
  后续若增加本机 CPU 密集功能，须重新比较；当前仍执行原有导航、主题与 1500 行日志性能门禁。
- **视图常驻：**创建过的视图留在场景里，切换时只改可见性：重新挂上场景会让 JavaFX 对整棵子树重新匹配全部
  CSS 选择器（流水线视图约 50 ms）。主题切换前先把隐藏的视图取下，只重排可见的一个；被取下的视图下次显示时
  再挂上，那一次付出重新匹配的代价。
- **主题只换一个样式类：**两套颜色都常驻，深色的令牌挂在根节点的 `dark` 样式类下；切换主题只增删这个类，
  不替换样式表（实测比替换主题文件快约一半）。
- **启动并行：**本机数据与服务在工具包启动的同时打开；窗口图标与卡顿监测在首帧之后。
- **请求不排队、可取消：**每类数据同时只有一个请求在途；“停止等待”中断 HTTP 交换本身，不留下挂起的连接。
- **退避与暂停：**后台不可达时拉长间隔，窗口最小化时停止轮询；暂停或恢复 DAG 的请求在途时不轮询 DAG 列表。
- **退出不等待：**关闭窗口时取消仍在途的请求（包括等待中的作业运行），进程立即退出；作业在引擎上继续。
- **动效有界：**状态环 420 ms、甜甜圈 520 ms、运行柱 240 ms、结果标记 320 ms；等待环只在等待作业结果且
  视图可见时转动，任务连线只在任务运行且流水线视图可见时流动。“减少动效”关闭这些动画。

## 回归

界面测试 `MainWindowTest.theFxThreadDoesNotStallOnceWarm` 在预热后启用 `FxWatchdog`：切换视图时记录到
超过 50 ms、切换主题时超过 100 ms 的停顿即失败；`aLogOfFifteenHundredLinesScrollsWithoutStalls` 对 1500 行
日志做同样的检查。打包每轮记录全部 20 次启动（见 [循环记录](loop/log.md)），任一次超预算都会失败，CI 保存完整 JSON。
监测线程每次采样前重新确认 FX 线程仍未回答，避免把监测线程自身被系统延后调度误报成界面停顿。
