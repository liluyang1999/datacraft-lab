# 流畅度

## 预算与实测

本轮 L8（2026-10-28）使用默认渲染器、32/256 MiB 堆和已训练的 AOT 缓存。
下表前三组为诊断补齐后代码 `7d508b7` 的验收，后续保留失败复测与各次实际修补后的验收。
这些历史数字来自 `ProcessHandle.startInstant` 的 OS 进程年龄估计；后续发现 Linux 的秒级
启动基准会造成偏差，因此不能当作精确耗时，也不与新计时直接比较。新算法见表后说明。
每组为 10 次新配置、10 次复用配置，全部计入，没有丢弃首次或较慢样本。
Windows 使用一级 JIT，Linux 保留默认分层编译，原因见下方“手段”。

`ae0f53c` 的远端 Windows 120 项与 20 次通过（599–685 ms），Linux 117 项通过，但旧计时
20 次中 19 次超过预算（1477–1637 ms）。核对
[JDK 25 Linux 实现](https://github.com/openjdk/jdk/blob/jdk-25-ga/src/java.base/linux/native/libjava/ProcessHandleImpl_linux.c)
发现 `startInstant` 使用秒级 `/proc/stat btime` 推算；隔离探针实际进程总时间 71.4–83.4 ms，
却报告 284–292 ms 的进程年龄。失败样本继续保留，这项发现不解释 Windows 历史尖峰。

打包验收改用父进程单调时钟 `perf_counter_ns`：在调用启动器前开始，每 5 ms 观察一次首帧日志，
向上取整到毫秒。启动器创建、JVM 初始化、日志刷新与观察调度延迟都计入；首帧的定义仍是第一个
CSS/布局脉冲完成后的回调，预算仍为 1500 ms。旧 OS 估计留在阶段诊断中，JSON 标明新计时依据。
观察线程在成功、失败和超时后都停止，缺失首帧、读取失败或运行时诊断不能当作通过。

两平台分别执行 120 / 117 项、确认 54 / 10 个原生库与每次 AOT 生效。
同次 Windows 的父进程测量比 OS 估计多 12–18 ms，Linux 的 OS 估计反而多 66–78 ms，
保留两者而不做常量扣除。训练首帧 Windows / Linux 为 1235 / 1571 ms，单列不受缓存启动预算约束。

历史尖峰尚未完整归因。此前失败样本为 2036 / 2614 / 1590 ms，应用代码与此前相同；
慢样本在入口、存储与工具包准备阶段已有延迟，不能归咎于某个页面。随后四次带 CPU 观察的
诊断启动为 1264 / 1186 / 1135 / 1123 ms，未复现尖峰；首个观察窗口的 CPU 峰值约 90%，
但没有与那三次失败同时采样，不能据此证明因果。类初始化追踪另观察到 D3D 原生初始化等待，
也不足以解释全部尖峰。诊断样本不替换失败的 20 次门禁，不调整渲染器、系统安全设置或预算。

补修提交 `9a4208d` 的远端两平台 20 次仍全部通过：Windows 562–801 ms（中位数 591.5），
Linux 1198–1330 ms（1266）。这证明该次环境下通过门禁，不推翻上述本机失败。
最初普通会话的 WPR 被拒绝（`0xc5585011`）；用户随后授权管理员采集。已用限定时长的管理员
辅助进程捕获 CPU 调度与磁盘事件，应用仍以普通权限运行。20 次带追踪启动为 1195–1495 ms，
事件丢失数 0；结束后确认 WPR 未在录制。操作依据见
[微软 WPR 文档](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/wpr-command-line-options)。

追踪发现 JavaFX 原生库从用户缓存加载。模块 jar 的本机库被保留为 jlink 资源，却没有安装到
运行时标准路径，导致每次启动重新解压、校验缓存。按
[OpenJFX 的加载规则](https://github.com/openjdk/jfx/blob/jfx25/modules/javafx.graphics/src/main/java/com/sun/glass/utils/NativeLibLoader.java)
补齐后，12 次交错对照的原路径中位数 / 最大为 1235 / 1360 ms，补包为 1099.5 / 1260 ms。
正式包 54 个 DLL 与源 jar 的 SHA-256 全部一致，完整 20 次验收通过且没有缓存回退。
编译线程数另做 18 次交错对照，没有稳定收益，未采用。上述修复减少了确定的启动成本，
不将未捕获的历史 2.6 s 尖峰归因于单一组件；后续仍执行原有严格门禁。

每次都是新进程；新配置会创建 SQLite，复用配置覆盖五个页面与浅深主题。
新计时覆盖父进程调用启动器到观察到第一个 CSS/布局脉冲完成的日志，确认每次 AOT 实际生效。
这不是显示器物理呈现时间，也没有清空操作系统文件缓存；不承诺任意机器或后台负载下的磁盘冷启动均达标。
训练过程本身不使用缓存，不混入正常缓存启动预算。当前远端结果见
[CI 40688429388](https://github.com/liluyang1999/datacraft-lab/actions/runs/40688429388)，
完整样本、历史训练耗时及失败记录见 [L8](loop/log.md#l8-启动与原生无障碍专项2026-10-28)。

历史提交的共享 Windows runner 曾有 2074 / 1929 ms 早期尖峰，严格门禁失败；新增阶段与 CPU 诊断
没有被当作性能修复。当前样本通过也不能证明此前尖峰的具体系统成因已经消除，后续仍执行相同严格预算。
历史同组较慢的 927 ms 样本与 559 ms 样本只相差 63 ms 进程 CPU，更符合等待或调度波动，
但尚不能据此指认具体系统组件。固定机器的本机验收和共享 CI 分别列示，不能互相替代。

| 指标 | 目标 | 本轮证据与边界 |
| --- | --- | --- |
| 视图切换 | ≤ 100 ms，首次 ≤ 200 ms | `69a7d04` 远端 Windows 120 项、Linux 117 项通过；每页真实绘制后才计作预热，首次绘制另受 200 ms watchdog 约束 |
| 主题切换 | ≤ 100 ms | Windows 原有门禁通过；伪类状态避免整树基础选择器重匹配，保留此前 CI 的 106 ms 失败记录 |
| 预热后的 FX 线程停顿 | ≤ 50 ms | Windows 完整门禁逐页滚动并核对全部 1500 行通过；原生交互另有两次初次显示期间的告警，没有异常，不能称为原生全程零告警 |
| 操作反馈 | ≤ 100 ms | 首次 HTTP/TLS 初始化在后台，取消、超时、关闭不会留下迟发请求；五项同步回归通过 |
| 内存 | 常驻 ≤ 250 MB | 保留 32/256 MiB 堆；188.1 MiB 工作集、375.7 MiB 私有提交为 L7 空状态历史抽样，本轮没有重做长期内存测量 |

阶段定位发现，尚未连接后台时也会提前创建 HTTP 客户端及 TLS，Linux 服务准备常比工具包晚约 100 ms。
改为首次请求时在后台共享初始化后，不再阻挡首屏。初始化等待仍计入请求总时限，过期请求不会迟发。
此前一版 Linux 的 20 个样本中有 1529 ms，门禁确实失败；该失败与最终全部样本保留在 L8，未提高阈值。
GC 交替对照没有稳定收益，因此没有修改 GC。软件渲染虽减少启动耗时，却在完整界面测试中内存不足，已撤回。
L7 的 1.314–3.283 s 等历史结果和负载条件保留在 [L7 记录](loop/log.md#l7-全面复核与边界打磨2026-10-28)。

启动优化的历史分解（2026-10-27，不带 AOT 缓存，改进前 → 改进后；不替代上方本轮结果）：

| 阶段 | 改进前 | 改进后 |
| --- | --- | --- |
| JVM 与 JavaFX 工具包启动 | 约 1.0 s | 约 0.9 s，与下一行并行 |
| 打开 SQLite（加载本机库）、DPAPI、HTTP 客户端（TLS 初始化）、JSON | 约 0.7 s，在工具包之后串行 | 在启动器里另起线程，与工具包启动并行 |
| 构建窗口（控件类加载、默认样式表、主题、第一个视图） | 约 0.55 s，含窗口图标 75 ms | 约 0.5 s；窗口图标改到首帧之后绘制 |
| 首次布局与渲染 | 约 0.3 s | 约 0.3 s |
| 合计到首帧 | 约 2.55 s | 约 1.7 s；带 AOT 缓存约 1.1 s |

AOT 缓存（JDK 25 的 JEP 483/514）记录启动时加载与链接的类，省去余下的大部分类加载。它只认 jar 组成的类路径，
所以由打包脚本生成（见 [README](README.md#打包)），`javafx:run` 从 `target/classes` 目录运行，不能使用。

## 手段

- **FX 线程只做界面：**网络、SQLite、JSON、加解密全部在后台；轮询的到点线程不读界面的列表与属性，
  只读后台线程可见的 `volatile` 副本。
- **就地更新：**轮询结果按主键与当前列表比较，只替换变化的元素（`Lists.reconcile`），表格不重建、
  不闪烁、不丢失选中与滚动位置；短列表（总览）只更新变化的行（`Rows`）。
- **合并更新：**同一轮询的新结果覆盖尚未应用的旧结果（`Latest`）；交付时再次检查代次，停止前排队的结果不再应用。
- **固定行高：**表格与列表设 `-fx-fixed-cell-size`，虚拟化只计算可见行。
- **有界日志页面：**Windows UIA 会请求 `ListView` 的屏外单元格，仅视觉虚拟化不能限制无障碍遍历。
  日志每页 100 行，保留全部模型中已读取的内容；末页跟随新日志，前页保留选择和滚动位置。
  200 行一页的中间版本仍出现 53 ms 样式匹配停顿，收紧到 100 行后完整门禁通过。
  侧滑面板关闭时移除源列表监听器。读取服务端下一段与本地翻页互不混淆。
- **少用特效：**阴影只用在通知、侧滑面板、菜单与提示，表格单元格里没有效果与渐变；侧栏开启缓存。
  侧滑面板的阴影绘在独立的静态底板上，日志滚动不重新模糊整块面板与其中的文字。
- **懒加载：**视图首次打开才创建，日志按段读取，侧滑面板关闭后释放内容与监听器。
- **堆边界：**打包与测试均使用 `-Xms32m -Xmx256m`，避免初始堆随主机内存扩大；同样的五视图空状态抽样中，
  调整前主进程工作集 248.9 MiB、私有提交 890.4 MiB。堆上限不是进程总内存上限，JavaFX 与本机库另占内存。
- **桌面编译策略：**Windows 的桌面包、测试及开发启动使用 `-XX:TieredStopAtLevel=1`，降低启动时 JIT 编译竞争。
  同机交替六次的默认策略中位数 / 最大为 1271 / 1424 ms，一级编译为 1127 / 1190 ms。
  代价是不使用 C2 的长期吞吐优化，因此只用于 Windows 的有界客户端；Linux 保留默认四级编译，
  避免限制软件渲染吞吐。引擎、Spark 与 API 进程保持原策略。
  后续若增加本机 CPU 密集功能，须重新比较；当前仍执行原有导航、主题与 1500 行日志性能门禁。
- **视图常驻：**创建过的视图留在场景里，切换时只改可见性：重新挂上场景会让 JavaFX 对整棵子树重新匹配全部
  CSS 选择器（流水线视图约 50 ms）。主题切换前先把隐藏的视图取下，只重排可见的一个；被取下的视图下次显示时
  再挂上，那一次付出重新匹配的代价。
- **主题使用伪类状态：**两套颜色都常驻，深色令牌由根节点的 `:dark` 状态控制。
  改变样式类会触发整树 `reapplyCSS`；伪类使用 JavaFX 的 CSS 状态转换，避免重新匹配全部基础选择器。
  这针对 Windows CI 捕获的 106 ms 字体度量停顿，仍执行原有 100 ms 主题切换门禁。
- **启动并行：**本机数据与服务在工具包启动的同时打开；窗口图标与卡顿监测在首帧之后。
- **请求不排队、可取消：**每类数据同时只有一个请求在途；“停止等待”中断 HTTP 交换本身，不留下挂起的连接。
- **退避与暂停：**后台不可达时拉长间隔，窗口最小化时停止轮询；暂停或恢复 DAG 的请求在途时不轮询 DAG 列表。
- **退出不等待：**关闭窗口时取消仍在途的请求（包括等待中的作业运行），进程立即退出；作业在引擎上继续。
- **动效有界：**状态环 420 ms、甜甜圈 520 ms、运行柱 240 ms、结果标记 320 ms；等待环只在等待作业结果且
  视图可见时转动，任务连线只在任务运行且流水线视图可见时流动。“减少动效”关闭这些动画。

## 回归

界面测试 `MainWindowTest.theFxThreadDoesNotStallOnceWarm` 在预热后启用 `FxWatchdog`：切换视图时记录到
超过 50 ms、切换主题时超过 100 ms 的停顿即失败；`aLogOfFifteenHundredLinesScrollsWithoutStalls` 对 1500 行
日志逐页遍历、逐条检查顺序和完整性，并做同样的停顿检查。打包每轮记录全部 20 次启动（见 [循环记录](loop/log.md)），任一次超预算都会失败，CI 保存完整 JSON。
监测线程每次采样前重新确认 FX 线程仍未回答，避免把监测线程自身被系统延后调度误报成界面停顿。
