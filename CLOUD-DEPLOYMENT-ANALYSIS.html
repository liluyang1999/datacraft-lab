一、工作负载画像（选型的硬约束）

选型的第一性问题不是「哪家便宜」，而是「这套负载到底是什么形状」。

组件形态常驻内存估算
Airflow api-server常驻 HTTP 服务~400–600 MB
Airflow scheduler常驻循环~400–600 MB
Airflow dag-processor常驻解析进程~300–500 MB
Airflow triggerer常驻异步事件循环~250–400 MB
Postgres 18（元数据库）常驻有状态数据库~200–400 MB
datacraft-api（JVM）常驻 HTTP 服务~150–300 MB
Spark 作业（local[*]）突发，driver+executor 同进程作业期间 +1–2 GB
Redis 8（仅多机 Swarm 需要）常驻 broker~50–100 MB

合计：空闲约 1.8–2.8 GB；跑 Spark 作业时约 3.5–5 GB。 因此 4 GB 是可用下限，8 GB 及以上才算宽裕；2 GB 会在作业期 OOM。

由此得出的第一条硬结论：本项目需要的是常驻的、有状态的虚拟机或容器主机—— 有长生命周期进程、有关系型数据库、有需要真实 CPU 与内存的批处理。 这条约束直接排除了所有「短时、事件驱动」的边缘/无服务器计算产品。

二、Cloudflare 的正确定位：不做计算，但值得用

Cloudflare 的计算产品（Workers、Pages、Durable Objects、Workers Containers）面向短时、事件驱动的边缘执行， 不是为「常驻 Airflow 调度器 + 关系型数据库 + JVM/Spark 批处理」设计的。 所以 Cloudflare 不能作为本平台的计算宿主——这不是价格问题，是产品形态不匹配。

但 Cloudflare 在免费层上能承担三个真实且有价值的角色：

能力在本项目中的作用价值
DNS + 反向代理域名指向主机并隐藏源站 IP推荐
Universal SSL免费 TLS 终结，免维护证书推荐
Cloudflare Tunnel不开放任何入站端口即可暴露 Airflow UI；主机可无公网 IP强烈推荐
Cloudflare Access（Zero Trust）在 Airflow UI 前加一层邮箱/SSO 鉴权（50 用户内免费）强烈推荐
R2 对象存储存放 Parquet 产出与 Postgres 备份。S3 兼容、零出流量费，免费额度 10 GB按需，很划算
Workers / Pages承载本项目的计算不适用

R2 值得单独强调：数据湖类产出（Parquet）与数据库备份放在 R2，比放 AWS S3 更省—— S3 的跨区/公网出流量要收费，R2 的出流量为零。而 datacraft-io 的 StorageService 端口设计本就便于后续接入 S3 兼容后端。

五、ARM 架构可行性核验（本次实测）

成本最优的两个方案（AWS t4g Graviton、Oracle Ampere A1）都是 ARM64。 这意味着一个常被忽略、但会直接让方案失效的前提：所有容器镜像必须有 arm64 变体。 我逐个查询了镜像清单，结果如下：

镜像支持架构ARM 可用
apache/spark:4.2.0-scala2.13-java25-python3-ubuntuamd64, arm64✅
apache/airflow:3.3.1amd64, arm64✅
eclipse-temurin:25-jreamd64, arm64/v8, ppc64le, s390x✅
maven:3.9-eclipse-temurin-25amd64, arm64/v8, …✅
postgres:18amd64, arm64/v8, …✅
redis:8amd64, arm64/v8, …✅

结论：ARM 方案技术上完全成立，六个镜像全部具备 arm64。 加上本项目的 JVM 制品是架构无关的字节码（Spark 为 provided，不打包任何本地库）， 因此在 x86 与 ARM 之间迁移无需重新适配代码。这使「用 ARM 省 20–40% 成本」成为可安全采纳的选项。

六、推荐方案

方案 A：零成本起步 先试这个

Oracle Cloud Always Free（Ampere A1，2 OCPU / 12 GB，东京或大阪）+ Cloudflare 免费层。 月成本 US$0，内存是需求的 3 倍，跑单机 Compose 栈非常宽裕。

代价要说清楚：A1 容量长期紧张，创建实例常遇 out-of-capacity 需反复重试； 免费层无 SLA；而且 Oracle 刚刚在没有任何公告的情况下把额度砍半、并终止超限实例—— 这说明该层级的条款可能再次单方面变更。因此：适合做实验与自用，不适合承载你不能丢的东西， 且务必把 Postgres 备份放到 R2 或本地。

方案 B：稳健低成本 长期主力推荐

AWS Lightsail 4 GB（东京）+ Cloudflare 免费层，约 US$20–26/月。 固定月价、账单可预测、含流量额度、快照备份简单。适合「希望它稳定跑着、不想操心」的场景。

方案 C：需要弹性时

EC2 t4g.medium（ARM）+ 1 年 Savings Plan + Cloudflare，约 US$19–23/月。 比 Lightsail 略便宜且能随时改机型、挂 EBS 快照、接 IAM/S3。代价是需要自己管安全组、EBS 与账单。

决策树

能接受「可能需要反复重试才能开到机器、且条款可能再变」吗？
├─ 是 → 方案 A：Oracle Always Free（$0）
│         └─ 之后若被回收或不够用 → 平移到方案 B（脚本云无关，迁移成本很低）
└─ 否 → 想要账单可预测、少操心吗？
         ├─ 是 → 方案 B：Lightsail 4 GB（约 $20–26）
         └─ 否，想要弹性与 AWS 生态 → 方案 C：EC2 t4g.medium + Savings Plan（约 $19–23）

延迟不敏感、只跑批处理、想把成本压到极限？
└─ 方案 D：Hetzner 欧美节点（约 $5–8），接受 200–250 ms 交互延迟
统一前提：无论选哪家，都先用单机 Docker Compose（LocalExecutor）， 仅当任务并发或高可用需求超出单机时再切 Swarm。本项目的部署脚本与编排文件是云无关的， 在任意 Linux 主机上都能跑，所以上述选择不构成厂商锁定，换家的成本主要只是重建主机与迁移 Postgres 数据。

七、安全与运维要点

  • 不开放入站端口：用 Cloudflare Tunnel 由主机向外拨出，Airflow UI 不暴露在公网，配合 Access 做鉴权。
  • 密钥管理：.env 仅适合单机起步；生产应改用 docker secret（Swarm）或云端密钥服务。.env 已在 .gitignore 中，切勿提交。
  • 备份：定期 pg_dump Airflow 元数据库并上传到 R2/S3。Postgres 大版本升级需 dump/restore，不能只换镜像标签。
  • JDK 补丁版本：Spark 4.2.0 将「早于 25.0.3 的 Java 25」标记为 deprecated。部署前确认镜像内 JRE ≥ 25.0.3（docker run --rm eclipse-temurin:25-jre java -version）。
  • 可观测性：单机阶段用 docker compose logs + Airflow 自带 UI 足够；上量后再考虑接入外部日志/指标。
