一、结论摘要

总体判断：项目已达到“个人单机数据处理平台可以放心使用和部署”的水平。 主干设计扎实：CLI、HTTP API 与 Airflow 共用同一个 DataJob 契约和执行引擎，模块边界清晰， 版本与安装约束集中管理，Linux CI 覆盖构建、真实 Spark、真实 Airflow 流水线、镜像和 Compose 栈。 本轮之前的主要缺陷不在正常路径，而集中在失败路径、跨平台行为、边界输入、部署默认值和文档漂移上。

本轮最重要的改进：

  • 失败语义统一。此前作业抛出 Error（例如在纯 JVM 镜像里调用 Spark 作业时的 NoClassDefFoundError）会逃出引擎：CLI 不写结构化结果，HTTP 请求永久挂起。现在除虚拟机级错误外，一律变为 FAILED 结果并记录完整堆栈。
  • 补齐“纯 JVM 覆盖小场景”这一既定需求。新增 datacraft-jobs 模块：csv-profile、file-checksum，复用 IO 端口，受数据根目录约束并带堆内存预算保护。
  • 数据安全边界。新增统一的 DATACRAFT_DATA_ROOT 约束（Spark 转换、纯 JVM 作业、Airflow 参数、部署栈），拒绝 Hadoop 通配符绕过；修复 SFTP 通配符误删/误覆盖、Windows 目录联接越界、下载截断旧文件等问题。
  • 安全与供应链。Airflow 3.3.2 / FAB 3.9.0（修复认证类 CVE）、Jackson 2.22.3、Checkstyle 14.1.0、带 SHA-256 校验的 Maven Wrapper、SHA 固定的 GitHub Actions、非 root 的 API 镜像、缺失密钥即失败、浏览器跨源请求 403。
  • 可验证性。JVM 测试用例从 73 增至 262；本机（Windows）首次能真实运行 HTTP 与 Spark 测试；CI 新增“每个模块确实执行了测试”的下限断言、jar 清单与算法探针、退出码冒烟。

仍需注意（详见第十节）：API 没有认证，只能留在回环地址或加认证网关后暴露；Swarm 多机配置只做过静态与桩测试，尚未在真实多节点验证； 本机 JDK 为 25.0.2，低于 Spark 4.2.0 建议的 25.0.3（构建会给出警告）；Spark 4.2.0 自带依赖存在当前不可达的公告，需等待上游修复版。

三、架构评估

执行主干

HTTP (datacraft-api)      CLI (datacraft-cli)      Airflow DAG (BashOperator)
        \                        |                         /
         \                       |      java -jar / spark-submit --class Runner
          +------------> JobExecutionEngine (datacraft-engine) <--------+
                                 |  catalog = JvmJobs + SparkJobs + BuiltInJobs
             +-------------------+----------------------+
             |                   |                      |
     BuiltInJobs [engine]   JvmJobs [jobs]        SparkJobs [spark]
      echo, noop            csv-profile,           spark-version,
                            file-checksum          csv-to-parquet, row-count
                                 |                      |
                        datacraft-io (StorageService, CsvFiles, SFTP)

评价：“一个契约、一个引擎、多种入口”的设计是本项目最大的优点，新作业只需实现 DataJob 并注册， 即可同时在 CLI、API 和 Airflow 中使用。本轮补上了此前的薄弱点：引擎现在对所有非虚拟机级错误给出统一的 FAILED 结果； 作业名必须是单个 URL 路径段且不能与 CLI 控制命令同名；Spark 作业在纯 JVM 环境中返回带有 spark-submit 提示的失败结果，而不是崩溃。

模块依赖（已由构建强制）

datacraft-common
  <- datacraft-config, datacraft-io, datacraft-engine
datacraft-engine
  <- datacraft-jobs (+ io), datacraft-spark, datacraft-api
datacraft-cli  -> api, engine, jobs, spark, io, config   (唯一的进程入口，打包为瘦 jar)

Spark 以 provided 作用域引入，CLI jar 约 9 MB，Spark 作业通过 spark-submit 运行； spark-submit --master 现在会被真正继承（此前 CLI 注入的 local[*] 会静默覆盖集群配置）。

五、本轮评估方法

  1. 基线：确认 GitHub 上最新提交 CI 全绿；在本机跑完整构建，记录 Windows 特有失败并查明原因 （其中 CLI 输出换行不一致是真实缺陷；Selector 失败源自用户 TEMP 目录无法承载 AF_UNIX 套接字，用 -Djdk.net.unixdomain.tmpdir 解决，而非此前记录的“JDK 缺陷”）。
  2. 分维度审查：引擎核心、IO、Spark、CLI/API、Airflow、部署、构建与 CI、文档准确性、依赖与漏洞、需求覆盖、安全共 11 个维度，共提出 137 项发现，每项附证据与失败场景。
  3. 独立复核：每项发现由另一方尝试反驳并尽量复现，驳回 3 项，确认 134 项（中 23、低 99、信息 12），去重后约 100 个独立问题。
  4. 归并为工作包：12 个文件互不重叠的工作包，外加按项目扩展规划新增的 WP-13（纯 JVM 作业模块）；28 项记为残余风险或路线图。
  5. 隔离实施与审查：每个工作包在独立的 git worktree 中实现，先写能在旧代码上失败的回归测试；再由独立审查方复核，4 个包按意见返修。
  6. 集成后审查：从 CI 预测、跨模块契约、JVM 正确性、安全等 5 个视角审查整体改动，确认 14 项，其中 3 项会直接导致 CI 失败（Linux 测试下限、Airflow 3.3.2 在 stdout 输出警告导致初始化脚本解析失败），全部在推送前修复并复验。
  7. 外部事实核实：版本、CVE/GHSA、Actions 标签与 Maven 分发包校验和均对照官方来源核实。

SFTP中间人攻击、误删/误覆盖JVM 客户端严格主机密钥；Airflow 下载要求 host_key；字面路径；原子下载低 需对真实服务器验收
部署机密弱默认值、泄露到进程参数或镜像独立随机生成、强度与独立性预检、:? 失败即停、stdin 传密码、.dockerignore中 所有 Airflow 容器共享机密，DAG/CLI/Spark 属管理员级可信代码
供应链被篡改的构建工具或依赖Wrapper SHA-256、Actions 固定 SHA、Jackson 旧版禁用、官方 constraints、基础镜像先拉取低 无持续漏洞扫描；基础镜像未固定 digest
Swarm 网络未加密覆盖网络、Redis 无密码有状态服务固定在数据节点；文档要求防火墙限制 2377/7946/4789中 多机前需加密与认证设计

九、部署与云成本

推荐先用单机 Docker Compose（LocalExecutor），Airflow UI 与 API 只绑定回环地址，经 SSH 转发或带认证的隧道访问：

python3 deploy/scripts/deployment_env.py init   # 生成独立随机机密，不覆盖已有文件
bash deploy/scripts/build-images.sh              # 拉取基础镜像并构建（DAG 与 jar 均打入镜像）
bash deploy/scripts/compose-up.sh                # 预检机密与端口后启动并等待健康

升级既有部署的注意事项（破坏性变更）：四个核心机密缺失时启动直接失败；DAG 目录不再绑定挂载，git pull 后必须重建镜像； Swarm 必须指定具体镜像标签（不能是 latest）并在管理节点登录镜像仓库；SFTP 连接必须配置 host_key； 非 50000 UID 的既有数据卷需一次性修复权限。完整步骤见 部署教程。

十、残余风险与路线图

优先级事项影响建议
P1API 无认证误暴露即可被任意调用保持回环；需要远程访问时在前面加认证网关
P1Swarm 未在真实多节点验证初始化服务、健康检查、工作节点排空只做过静态与桩测试真正扩展到多机前，先配置共享存储、加密覆盖网络与 Redis 认证，并做一次演练
P1JDK 补丁级别本机 25.0.2 低于建议的 25.0.3；Temurin 25.0.4.1 镜像尚未发布，镜像仍继承 25.0.4+7升级本机 JDK 后把 Enforcer 下限提升为硬性要求；上游标签发布后重建镜像
P2Spark 4.2.0 自带依赖的公告Jackson 2.21.2、Netty、Jetty 存在公告，当前配置下不可达不发布 Spark UI/RPC 端口；Spark 4.2.1 发布后升级
P2机密在 Airflow 容器间共享任一任务代码可读取全部机密视为可信代码边界；多租户前再做机密隔离
P2无持续依赖/漏洞监控SHA 固定的 Actions 与依赖会逐渐过时经所有者同意后启用 Dependabot 与定期 SCA 扫描
P3Spark 会话锁无超时、durationMillis 含排队时间、Lifecycle 仅为标签、编译告警未设门禁当前部署拓扑下不触发引入 HTTP 侧 Spark 服务或多租户时再处理
